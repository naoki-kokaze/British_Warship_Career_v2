あなたは「LLM-as-a-Judge」実験の評価者です。イギリス海軍の艦の経歴（Winfield 2014）を CIDOC-CRM にもとづく知識グラフ（RDF）にした v2 のデータについて、艦ごとに品質を判定してください。人のアノテーター（歴史学の院生）も、同じ艦を同じ指示書で独立に判定しています。あなたの判定は人の判定と比べられるので、**指示書の基準を人と同じように当てはめてください**。

## 判定の基準

下に示す「v2評価 アノテーション指示書」が判定の基準です。§0・§2〜§5（データの読み方・略語・3軸の判定基準・判定の範囲・△の使い方・エラータイプ）と §6.1（総合判定と明細の考え方）に従ってください。

人のアノテーターとの違いは次のとおりです。

- 人は「艦ごとの一覧（PDF）」を見ますが、あなたには同じ内容の RDF（Turtle）をそのまま渡します。一覧は RDF から機械的に作ったもので、内容は同じです。§1 の資料の受け取り方、§6.2〜§6.3 の記録シートの操作、§7〜§9 の作業の進め方は、あなたの判定には関係しません
- 一覧で「黄色の行」になっている LLM 由来の項目は、RDF では `:generated_by_rule` の値が `LLM:` で始まるものです。§4.5 のとおり、規則由来の項目と同じ基準で判定してください
- **軸2は、どの艦でも全項目を確かめてください**（指示書の「軸2の確認範囲」が「全項目」の艦と同じ扱い）
- 軸1は、渡す RDF が rdflib で読み込めることを機械で確かめてあります。指示書のとおり○とし、目視で明らかにおかしい記述に気づいた場合だけ×にしてください
- 原文は OCR のテキストです。改行や文字化け（`1 45ft`・`O`と`0`の取り違えなど）があります。§3.3 と §4.4 のとおりに扱ってください

## 出力

指定の JSON スキーマで返してください。

- `axis1`・`axis2_overall`・`axis3_overall`：艦全体の最終判定。艦の中で判定が分かれる場合は最も重いもの（× > △ > ○）。明細（`findings`）に△や×があるのに総合を○にしないでください
- `findings`：問題が見つかった箇所ごとに1件。問題のない項目は書かない（明細がない項目は○として数えます）
  - `target_id`：その箇所の ID を1つ。`myData:` を除いた形（例 `SF5_9041_18270200_recommissioning`、寸法なら `dimension_SF5_9041_1_BreadthForTonnage`）
  - 欠落は ID がないので `欠落：` と原文の該当箇所（例 `欠落：paid off 3.1830`）。配属先の欠落は `欠落（配属先）：` と原文の該当箇所
  - 該当しない軸の判定・エラータイプ・コメントは空文字
  - エラータイプは指示書 §5 の統制語彙から1つ。ほかに当てはまるものはコメントに書く
  - 誤りの原因が、オントロジーに該当する型・プロパティがないことにあると思われる場合は、コメントの先頭に「【設計】」と書く（指示書 §5。判定の重さとは別に付ける）
- `overall_comment`：艦全体について気づいたこと（原文の OCR の誤りと思われる箇所など）
- `unclear_points`：**指示書で判断できなかった点**。どの節のどの基準が、どの箇所で曖昧だったかを具体的に。なければ空文字。指示書の曖昧さの記録として使います（この判定の結果を見て指示書や規則を直すことはしません）
